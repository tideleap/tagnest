# A3 统计报告页 — 设计决策（B-6a）

日期：2026-08-15 · 状态：已定稿，进入实施

## 现状盘点（调研结论）

| 报告板块 | 数据源 | 状态 |
|---|---|---|
| 库规模 | `GET /api/stats`（bookmarks/favorites/archived/trashed/untagged/addedLast7Days/tags） | ✅ 已有，useStats |
| 健康分 | `GET /api/bookmarks/health`（HealthReport.score + duplicateGroups + orphanTags） | ✅ 已有，useHealthReport |
| AI 贡献度 | `GET /api/ai/overview`（aiTagLinks/userTagLinks/usage/contribution/feedback） | ✅ 已有，useAiOverview |
| 标签分布 | `GET /api/tags`（每标签带 count） | ✅ 已有，useTags |
| 收藏趋势 | **无聚合端点**（TimelinePage 是书签列表分桶，非计数） | ❌ 唯一缺口 |

## 关键决策

### D1：唯一新端点 `GET /api/stats/trend`

```
GET /api/stats/trend?days=180
→ { days: [{ date: 'YYYY-MM-DD', count: number }] }
```

- 按天分桶最近 N 天（默认 180，上限 365）的新增书签数。
- SQL：`SELECT substr(created_at,1,10) AS d, COUNT(*) FROM bookmarks WHERE user_id=? AND deleted_at IS NULL AND created_at >= ? GROUP BY d`——走 `idx_bm_user_live_created (user_id, deleted_at, created_at DESC)` 索引，只读聚合。
- 前端补齐无数据的日期为 0（后端只返回有数据的桶，响应体小）。
- 私密过滤：PRIVATE_BOOKMARK_CLAUSE 注入（与 stats.ts 口径一致）。

### D2：报告页 = 纯组合层，零新聚合逻辑

`/report` 页只组合 5 个现有 hooks（useStats/useHealthReport/useAiOverview/useTags/useTrend），不新建聚合端点群。**数据口径与 metrics 一致**的完成标准由此天然满足——同一端点同一 SQL。

### D3：渲染性能

- 页面 lazy 加载；5 个查询并行发起（TanStack Query），最慢的 health 报告是纯 SQL 秒回。
- 标签分布只取 Top 15（按 count 降序），其余归「其他」，避免大标签库渲染爆炸。
- 趋势图用纯 SVG/CSS 条形（项目既有风格，AiMetricsPanel 同款），不引入图表库。

### D4：导航入口

侧边栏「时间线」之后加「报告」（BarChart3 图标），路由 `/report`（RequireAuth + AppLayout 内）。

## 隐私

所有端点已含 user_id 隔离 + PRIVATE_BOOKMARK_CLAUSE；报告页不暴露任何私密内容，只读计数。

## 测试计划

- `tests/stats-trend.test.ts`（新）：按天分桶正确性、days 参数边界（默认/上限）、私密书签不计入、他人数据隔离。
- dbMock 扩展：trend 的 GROUP BY 查询处理器。
- 前端：ReportPage 组件测试（mock hooks，断言各板块渲染与 Top15 截断）。

## 已知限制

- 趋势只统计存活书签（deleted_at IS NULL），已删书签的历史新增不回溯——与 stats 口径一致。
- 无导出/分享能力（报告是只读内览页）。
