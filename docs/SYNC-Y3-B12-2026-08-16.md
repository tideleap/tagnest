# B-12 浏览器书签双向同步（Y3）可行性评估与决策记录

> 来源：任务 #197（V2 评估项，依赖 B-1 扩展先行，已完成）。
> 范围：**仅评估，不进入实施**。本文件为评估报告 + 决策记录。
> 竞品参照：bookmark-syncer（AGPL-3.0）的「WebDAV 自托管跨浏览器同步 + 同步前快照回滚」。

## 1. 背景与目标

产品升级方案将「浏览器书签双向同步」列为 V2 评估项（Y3）。目标：让用户的浏览器原生书签与 TagNest 书签库保持一致——浏览器里增删改书签回流到 TagNest，TagNest 里增删改也写回浏览器。

本评估回答三件事：**冲突怎么解、隐私怎么保、流量多大**，并给出是否实施的决策。

## 2. 现状核查（代码证据，非记忆）

**扩展（extension/）** —— `extension/manifest.json`：
- `permissions: ["activeTab", "tabs", "storage", "scripting"]` —— **没有 `bookmarks` 权限**。
- 现仅能做「出站保存」：`bg/api.js` 的 `ensureBookmark`（POST /api/bookmarks，409 去重）、`patchBookmark`（PATCH）、`appendNote`；`capture-window.js` 把当前窗口标签批量存入 TagNest。`save-page` / `capture-window` 两个命令均为「浏览器 → TagNest」单向。
- **结论**：扩展今天读不到浏览器书签树。双向同步的第一个硬前置是申请 `bookmarks` 权限（会触发存量用户重新授权弹窗）。

**后端（functions/）** —— `migrations/0001_init.sql` 的 `bookmarks` 表：
- 列：`id, user_id, url, url_key, title, description, favicon_url, cover_url, note, ai_summary, is_favorite, is_archived, visit_count, last_visited_at, created_at, updated_at, deleted_at`。
- 有 `updated_at`（且 `idx_bm_user_live_updated` 按 `updated_at DESC` 索引），适合做「某时间点之后的变更」水印查询；但 **没有 per-field 版本向量、没有 etag/version 列、没有 change-log 表**。
- `url_key` 唯一（归一化 URL）天然可做跨端去重主键。
- 无 `functions/api/**/sync*` 端点 —— 同步协议需从零建设。
- 可复用原语：`O8` 字段级加密（`functions/_lib/crypto.ts` AES-GCM）、`PRIV-1/PRIV-2` 零知识/类别私密（服务端只存密文、从所有列表隐藏）；`ApiException`/`badRequestCode` 错误范式；`ensureTags` 标签链接。

## 3. 推荐方案：变更日志（hub-and-spoke）

采用「TagNest 后端为枢纽（hub）、各浏览器扩展为 spoke」的星型模型，而非端到端 P2P：

- **单一事实源**：以 TagNest `bookmarks` 表为准。浏览器书签是「本地镜像 + 待同步意图」，避免双主互写最难的那类冲突。
- **水印**：客户端保存 `lastSyncedAt`（服务端 `updated_at` 游标）。同步时：
  - 拉取：`GET /api/bookmarks/sync?since=<watermark>` 返回 `updated_at > watermark` 且未删除/已删除的书签增量（含 `deleted_at` 以传播软删）。
  - 推送：扩展把本地对浏览器书签树的增/删/改，转换成对 TagNest 的 `POST`/`PATCH`/`DELETE` 批量（复用现有 endpoints，无需新写 CRUD）。
- **增量落地**：后端可直接用 `updated_at` 游标 + `deleted_at` 满足「增量拉取」；推送侧复用现有 CRUD，由 `url_key` 去重保证幂等。若需更精细水印，最小方案是给 `bookmarks` 加 `sync_rev INTEGER`（每次写自增）。

## 4. 冲突策略

四种候选，按复杂度 / 保真度排序：

| 策略 | 实现成本 | 保真度 | 评价 |
| --- | --- | --- | --- |
| 整项 LWW（按 `updated_at`） | 低 | 低 | 并发改不同字段会互覆盖，丢数据 |
| **字段级 LWW**（title/url/note/tags 各自时间戳） | 中 | 高 | 推荐：note/标签等独立合并，仅同字段并发才 LWW |
| 3-way merge（同步前快照基线 + 共同祖先） | 中高 | 高 | bookmark-syncer 套路：快照回滚，适合「先拉后写」 |
| CRDT / 版本向量 | 高 | 最高 | 过度工程，书签量级不需要 |

**推荐：字段级 LWW 为主，叠加「同步前快照」兜底回滚。**
- 每个可变字段带自己的 `updated_at`（或统一用一张 `bookmark_revisions`）；同字段并发以较新者胜，不同字段变更互不干扰。
- 每次同步前，扩展把「当前浏览器书签树」存一份本地快照（bookmark-syncer 的 pre-sync snapshot 模式），若合并后结果异常，用户可一键回滚到快照。
- 真正不可自动调和的硬冲突（如两端把同一 URL 改名成完全不同标题且都不记得基线）→ 标记 `conflict` badge，前端展示让用户手动选，不静默丢数据。

## 5. 隐私

书签 URL/标题属于浏览行为画像，敏感度高。

- **传输**：扩展已走 HTTPS + 应用级 API Key（`O5` 体系），同步通道复用即可，无新增暴露面。
- **静态**：`bookmarks` 是 FTS5 全文检索的核心表，整列加密会破坏搜索，故**不**对普通书签做服务端加密；敏感书签本就走 `PRIV-1` 零知识保险库（服务端只存密文）。同步层面对「待同步 payload」可加**可选端到端加密**（对称密钥存扩展 `storage`，密钥不出端），作为 Phase B 增强。
- **权限面**：`bookmarks` 权限授予后扩展可读写**全部**浏览器书签——必须在隐私政策与弹窗中明确告知，且提供「仅同步到 TagNest 的收藏」开关（默认只上行、不回写浏览器，降低风险）。
- **撤回**：用户可随时在扩展 `options` 页撤销 `bookmarks` 权限 / 清除 `storage` 中的同步状态。

## 6. 流量

- **模型**：变更日志 = 仅增量。典型用户 1k–5k 书签，日变更个位数到几十；每次同步只传 diff，不是全量。
- **首次 / 周期快照**：全量书签树仅在首次同步与「周期快照」（如每周）传输一次，用于基线对齐与回滚；体积 ≈ 每条 0.5–1KB（URL+title+tags），5k 条约 2.5–5MB，一次性可接受。
- **拉取**：`GET /api/bookmarks/sync?since=` 走 `idx_bm_user_live_updated` 索引，O(增量)，服务端成本低。
- **回滚快照**：存扩展本地 `storage`（不进服务端），零额外流量。

## 7. 风险与未决

- **R1 权限升级弹窗**：加 `bookmarks` 权限会让已装用户看到「扩展要求新权限」提示，可能吓退部分用户。缓解：Phase A 仅请求权限 + 只读对账，把「回写浏览器」作为可选项默认关闭。
- **R2 双根真相**：即便 hub-and-spoke，浏览器本地删除 vs TagNest 编辑仍可能冲突；靠字段级 LWW + 快照 + 手动冲突解决兜底。
- **R3 软删语义**：浏览器书签删除 = 真删；TagNest 是软删（`deleted_at`）。拉取时须把 `deleted_at` 映射为浏览器侧删除，但保留服务端可恢复——UI 须提示「同步会清空浏览器侧对应书签」。
- **R4 扩展商店审核**：读写全部书签的扩展在 Chrome Web Store 需说明用途，可能触发额外审核。

## 8. 决策记录

**决策：建议进入实施，分两阶段；先 Phase A 低风险探路，再 Phase B 完整双向。**

理由：
1. 技术可行，且后端 `updated_at` 索引、CRUD 端点、O8/PRIV 原语均已就绪，增量成本低。
2. 真正风险（权限弹窗、双根冲突）可由「Phase A 仅上行 + 只读对账」吸收大部分，不一次性放开改写能力。
3. 与产品差异化叙事一致：数据在用户自己的 Cloudflare 账户 + 可选 E2E + 随时完整导出。

**阶段拆分（若批准，转为 B-12 实施任务）：**
- **Phase A（只读对账 / 单向上行增强）**：扩展 `manifest.json` 加 `bookmarks` 权限；新增「同步对账」视图——拉取 TagNest 增量、与本地书签树 diff、只读展示「浏览器有 / TagNest 有 / 不一致」三态；不改写浏览器。验证同步模型与权限体验。
- **Phase B（变更日志双向）**：后端加同步水印端点（+ `bookmark_revisions` 或 `sync_rev`）；扩展实现推送本地变更 + 拉取并回写浏览器 + 同步前快照回滚；冲突 badge + 手动解决；可选 E2E。

**不实施的情形**：若 Phase A 实测权限弹窗导致显著流失、或冲突率不可接受，则退回为「单向上行 + 定期导入」终态，不在 V2 做双向。

## 10. Phase A 实施（已交付 2026-08-16）

用户批准分阶段实施，本阶段仅交付 **只读对账模型**（不改写浏览器），验证同步协议与权限体验。

**后端**：新增只读端点 `GET /api/bookmarks/sync-keys`（functions/api/bookmarks/sync-keys.ts）。
- 鉴权 `requireUserId`；返回 `{items:[{id,urlKey,updatedAt,title}], cursor, hasMore}`，`Cache-Control: no-store`。
- 游标分页 `(updated_at ASC, id ASC)`，复用 `idx_bm_user_live_updated`；排除 `deleted_at IS NULL` 且 `is_private=0` 且非私密标签（口径与 `listBookmarks` 一致，E2E 加密行不含明文 url 不污染对账集）。
- 仅返回轻量字段，5k 书签库对账流量约 2.5–5MB，远低于拉全量对象；该端点同时为 Phase B 增量同步复用。

**扩展**（纯 JS MV3，无构建步骤）：
- `manifest.json` 加 `"optional_permissions": ["bookmarks"]`（保留原 `permissions` 不变）——权限**按需授权**：用户在对账页点「授权并对账」才弹 `chrome.permissions.request`，规避安装即强制弹窗（R1 缓解）。
- `extension/bg/sync-diff.js`：无 `chrome.*` 引用、可被 vitest 导入。**忠实移植** `urlKey`（tracking 参数剥离/host 小写去 www/去尾斜杠/参数排序），`flattenBrowserBookmarks(tree)`，`diffByKey(browserList, tnList)` → `{onlyInBrowser, onlyInTagNest, both}`。
- `extension/bg/reconcile.js`：`collectBrowserBookmarks()`(`chrome.bookmarks.getTree`) + `fetchTagNestKeys(cfg)`(游标拉全 sync-keys) + `reconcile(cfg)`。
- `extension/reconcile.html` + `reconcile.js` + `reconcile.css`：只读对账页（授权 → 三态列表，仅展示不改写），`popup.html`/`popup.js` 加「同步对账」入口按钮打开该页（新标签页）。

**测试**（17 例全绿，已并入全量门禁）：
- `tests/sync-keys.test.ts`（5）：用户隔离 / 排除 deleted+private / 游标翻页覆盖全量 / 末页 hasMore=false+cursor=null / no-store 头。
- `tests/sync-diff.test.ts`（12）：**跨语言一致性**——对 9 组样例断言扩展 `urlKey` 与后端 `functions/_lib/urlkey.ts` 的 `urlKey` 逐字节相等（保证浏览器书签与 TagNest 孪生日精确匹配）；`flattenBrowserBookmarks` / `diffByKey`（含 utm 噪声去重）。

**门禁**：typecheck ✓、lint ✓（0 error）、build ✓（剥离 `genie-safe-delete` 预载 `NODE_OPTIONS="--use-system-ca"`）、全量 vitest ✓、UTF-8 ✓。提交并安全推送 origin/main 触发部署。
