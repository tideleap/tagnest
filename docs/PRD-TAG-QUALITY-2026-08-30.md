## 1. 原始需求

> "什么玩意，AI 整理的一坨屎一样，一点没有智能的感觉，重新优化整理的逻辑，避免出现孤立标签太多，标签数量控制到一定范围以内"

拆解为三条可验收的产品诉求：

| # | Owner 原话 | 翻译为产品诉求 | 当前是否满足 |
|---|---|---|---|
| R1 | "一点没有智能的感觉" | 标签要有**体系感**：能复用已有词表、有层级、头部标签能撑起主干，而不是一堆平铺的关键词 | ❌ 词表只是 prompt 里的软建议；`synthesizeTaxonomy` 仅在 `synthesizeTree` 开启且 `tagCounts.size >= 8` 时才跑 |
| R2 | "孤立标签太多" | 只关联 1 个书签的一次性标签必须被消灭 | ❌ `resolveCandidates` 后无最小支持度校验 |
| R3 | "标签数量控制到一定范围以内" | 一次整理产出的**不同标签总数**要有上限 | ❌ 只有 per-bookmark 的 `maxTags=4`，无全局预算 |

---

## 2. 产品目标（2 句话）

1. **让 AI 整理结果从"关键词堆砌"变成"可浏览的标签体系"** —— 一次整理产出的不同标签数受全局预算约束、每个标签至少承载 2 个以上书签、70% 以上的标签分配落在用户已有词表上。
2. **让这一切无需用户配置即可生效** —— 治理作为整理管线的内置阶段自动运行，用户感受到的只是"整理完看着舒服了"。

## 4. 关键产品决策（含具体阈值推荐）

### 4.0 决策总览

| 决策点 | 推荐值 | 一句话理由 |
|---|---|---|
| 每书签标签数上限 | 默认 **4**，可调范围收窄为 **2–6**（现状 1–8） | 4 是"够用不稀释"的经验值；8 个标签等于没打标签 |
| 每书签软下限 | **2**（非硬下限，见 4.1） | 单标签书签缺乏检索维度，但不强塞垃圾标签 |
| 全局不同标签预算 | **D_max(N) = min(100, max(6, ceil(N/3)))** | 保证平均支撑度 ≥ 7.5；100 是人工可浏览上限 |
| 新标签最小支持度 | **minSupport = 2**（P1 升级为自适应） | 2 是"消灭孤立标签"的最小充分值 |
| 孤立标签处置 | **合并 → 上卷 → 丢弃+域名兜底**（三级降级） | 逐级保底，保证不会有书签被"治理"成 0 标签 |
| 新标签占比上限 | **≤ 30% × D_max** | 迫使模型优先复用，避免每批都重建词表 |
| 设置页暴露 | **P0 不暴露任何新参数**；P1 提供「精简/均衡/细致」三档预设 | owner 要的是"AI 自己做好"，不是更多旋钮 |

### 4.1 a) 每个书签的标签数

| 项 | 现状 | 推荐 | 依据 |
|---|---|---|---|
| 上限 `maxTags` 默认 | 4 | **保持 4** | 4 个标签足以覆盖"主题 + 类型 + 平台 + 用途"四个维度，是书签管理器的通行默认 |
| 可调范围 `clampMaxTags` | `[1, 8]` | **收窄为 `[2, 6]`** | 8 个标签/书签会让标签失去区分力——如果一个书签需要 8 个标签才能描述，说明标签体系本身碎了；下限 1 会导致大量单标签书签，与 R2 的方向相反 |
| 软下限 `minTags` | 无 | **2** | 定义：当某书签有 ≥2 个候选通过质量门槛时，必须取满 2 个；仅 1 个通过时允许只取 1 个（**不强行补位**）；0 个时用 `domainFallbackTag` 兜底 |
| 质量门槛 | 无 | `conf ≥ 0.35` **且** `conf ≥ 0.5 × 该书签最高 conf` | 绝对门槛拦垃圾；相对门槛保证 Top-1 永远不会被自己的门槛误杀（防止模型整体低置信时全量清空） |

**目标分布（P0 验收用）**：

| 每书签最终标签数 | 目标占比 |
|---|---|
| 1 个 | ≤ 10% |
| 2 个 | ~30% |
| 3 个 | ~35% |
| 4 个（满） | ~25% |
| 0 个 | ≤ 1%（其余走域名兜底） |

### 4.2 b) 一次整理任务产出的「不同标签总数」上限

**推荐公式（P0）**：

```
D_max(N) = min( 100, max( 6, ceil( N / 3 ) ) )
```

- `N` = 本次整理任务实际参与的书签数
- `k = 3`：密度系数，含义是"平均每 3 个书签最多产生 1 个新标签"
- 上限 `100`：一个人在侧边栏能**浏览**（而非搜索）的标签量级上限，超过 100 就只能用搜索，标签作为浏览入口的价值归零
- 下限 `6`：极小批量（N < 18）时保底给 6 个标签，避免 10 个书签被硬塞进 3 个标签导致过度粗化

**为什么是 k=3 而不是 2 或 4**：
- `k=4`（D ≤ N/4）过严：N=168 → 42 个标签，语义粒度偏粗，技术类书签会大量挤进同一个"前端"标签下，反而丢掉区分度（R1 反向受损）
- `k=2`（D ≤ N/2）过松：N=168 → 84 个标签，平均支撑度只有 5，仍会残留不少"2~3 个书签"的准孤立标签，R2 解决得不彻底
- `k=3` 在两者之间，且**在 N ∈ [18, 300] 区间内平均支撑度恒定 ≈ 7.5**（推导：分配总数 ≈ 2.5N，D = N/3，支撑度 = 2.5N ÷ (N/3) = 7.5），这个数值既能让标签"点开有内容"，又不至于粗到没区分度

**换算表（按治理后平均每书签 2.5 个标签估算）**：

| N（书签数） | ceil(N/3) | **D_max** | 预计平均支撑度 |
|---|---|---|---|
| 10 | 4 | **6**（触下限） | 4.2 |
| 20 | 7 | **7** | 7.1 |
| 50 | 17 | **17** | 7.4 |
| 100 | 34 | **34** | 7.4 |
| 168（owner 实测批） | 56 | **56** | 7.5 |
| 200 | 67 | **67** | 7.5 |
| 300 | 100 | **100**（触上限） | 7.5 |
| 500 | 167 | **100** | 12.5 |
| 1000 | 334 | **100** | 25.0 |
| 3000 | 1000 | **100** | 75.0 |

> 超大库（N > 300）被 100 封顶后标签会变粗，这是**有意的设计取舍**：此时用户靠搜索和智能集合找书签，标签退化为"顶层导航"，与 `SMART-COLLECTIONS-B8` 的定位不冲突。

**预算分配规则（Top-D 截断）**：
1. 对候选标签按 `score = 有效支持度 × 2 + Σ(置信度)` 降序排序（**支持度权重高于置信度**——被多个书签共同指向，比模型单次高置信更可信）
2. 取前 `D_max` 个进入「保留集」
3. 保留集内若存在「新标签且有效支持度 < minSupport」，剔除并顺延补位
4. 落选标签进入 4.3 的降级流程

### 4.3 c) 孤立标签（singleton）如何处理

**先明确判定口径**（关键，避免误伤）：

```
有效支持度(effectiveSupport) = 词表中已有 count + 本次批次内新增的书签数
```

- 一个标签在**本批次**只被 1 个书签使用，但用户在别处已经用了 20 次 → **不是孤立标签，必须保留**
- 只有「**全新标签** 且 批次内支持度 = 1」才是治理对象

**三级降级策略（按顺序尝试，命中即停）**：

| 优先级 | 策略 | 适用条件 | 说明 |
|---|---|---|---|
| ① | **合并到近义标签**（Merge） | 在保留集/词表中存在相似度 ≥ **0.75** 的标签（复用 `findDuplicateClusters` + `aliases.ts` + `canonicalSiteLabel`） | 最优解：保住了具体语义。`React Hooks` → `React`、`工具类` → `工具` |
| ② | **上卷到父标签**（Rollup） | 合并未命中，但该标签存在父节点（复用 `taxonomy-tree.ts`），或能确定唯一上位词 | 次优：语义变宽但仍有意义。`Vue3 源码解析` → `前端` |
| ③ | **丢弃 + 域名兜底**（Drop） | 既无近义、也无父节点，且有效支持度 = 1 | 直接放弃该分配；若该书签因此变成 0 标签，则用 `domainFallbackTag` 补 1 个（**保证不会治理出 0 标签书签**） |

**为什么按"合并 → 上卷 → 丢弃"排序**：合并保住的是更具体的语义（丢的信息最少），上卷牺牲具体度换取支撑度，丢弃是最后手段。反过来做会先把 `React Hooks` 上卷成 `前端`，白白丢掉一层有效信息。

**边缘情况**：有效支持度 = 2 但两个书签都是同一 host（如 `github.com/a`、`github.com/b`）→ 仍算通过（host 相同恰恰说明语义相关），但**不计入头部集中度分子**，避免同站刷量制造虚假主干。

### 4.4 新标签创建的准入门槛

| 项 | 推荐值 | 依据 |
|---|---|---|
| **最小支持度 `minSupport`** | **2** | 2 是消灭 singleton 的最小充分值。取 3 会让小批量（N<30）几乎无法产生任何新标签，首次整理会退化成"只能复用不存在的词表"，体验更差 |
| P1 自适应升级 | `minSupport = max(2, min(10, ceil(N × 0.005)))` → N=168→2、N=500→3、N=1000→5、N≥2000→10 | 大库里"2 个书签"相对占比过低，容易被淹没在尾部；0.5% 是经验平衡点 |
| **新标签数量配额** | `newTagQuota = min(0.3 × D_max, D_max − 已复用标签数)` | 强制模型优先复用。0.3 的理由：允许体系有机生长，但不允许每批推倒重来 |
| 置信度门槛 | 新标签 `conf ≥ 0.5`，复用已有标签 `conf ≥ 0.35` | 造新词的风险高于复用，门槛应对称性提高 |
| 命名规范 | 复用 `canonicalSiteLabel`；长度 2–12 字；禁止纯数字、纯符号、URL 片段、与父标签同名 | 与 `AI-ORGANIZE-HANDOFF.md` 的站点命名单一真源保持一致 |

### 4.5 治理管线的架构决策（给架构师）

**决策：P0 采用「纯算法治理」，治理阶段零额外模型调用。**

理由：
1. 项目刚经历 `0/168 + 请求超时` 事故（`AI-ORGANIZE-HANDOFF.md`），任何新增模型调用都是延迟与成本风险
2. 支持度统计、预算截断、近义合并、上卷全部可确定性复现 → **可单测、可回归**，符合"质量治理"这个需求本身对可验证性的要求
3. 模型仲裁（P2）只作为算法判不准时的兜底升级手段

**管线改造位置（关键）**：

```
现状:  for each batch → tagGroup → applyItem → [synthesizeTaxonomy] → renameByFeedback
       → resolveCandidates → score → slice(0, maxTags) → 写回 + 写缓存
                                                          ↑ 问题：每个书签各自截断，没有全局视野

改造后: for each batch → tagGroup → applyItem
       → 【新增】governTaxonomy(modelTags, vocab, N)   ← 全局统计 + 预算 + 合并 + 上卷 + 降级
       → synthesizeTaxonomy（治理后跑，输入更干净）
       → renameByFeedback → resolveCandidates → score → slice(0, maxTags) → 写回 + 写缓存
```

**⚠️ 两个必须注意的副作用（P0 验收项）**：

1. **缓存写入时机**：`engine.ts:388-395` 目前在每个 batch 内就把 `item.tags` 写进缓存。治理前写缓存 = 把未经治理的碎片标签永久固化，下次同 URL 直接命中缓存、绕开治理。**必须把缓存写入移到治理之后。**
2. **执行时序**：治理需要全批次的 `modelTags` 统计，因此必须在**所有 `tagGroup` 分批调用完成之后**统一执行，不能逐批治理。

### 4.6 是否需要在设置页暴露新参数

**推荐：P0 一个都不暴露。**

| 理由 | 说明 |
|---|---|
| 与 owner 诉求相反 | owner 说的是"一点没有智能的感觉"——他要的是 AI 自己判断更好，不是给他更多旋钮自己调 |
| 参数不是用户偏好 | `minSupport`、`D_max` 是**算法质量参数**，用户无法预判"设成 3 会怎样"。可解释的用户偏好只有"我想要更粗还是更细" |
| 成本 | 每个新设置项都要 schema 迁移 + 校验 + 帮助文案 + 前端状态管理，收益远低于成本 |
| 已有的 `maxTags` 够了 | 设置页「整理策略」已有「每条书签最多推荐」（`AiSection.tsx:281-287`），保留即可，仅把选项从 1–8 收窄为 2–6 |

**P1 提供单档替代方案**：新增一个「标签粒度」三档预设（**不是**暴露 6 个滑块）：

| 档位 | maxTags | 密度系数 k | minSupport | 面向 |
|---|---|---|---|---|
| 精简 | 3 | 4（D ≤ N/4） | 3 | 大库、追求强聚类 |
| **均衡（默认）** | 4 | 3（D ≤ N/3） | 2 | 绝大多数用户 |
| 细致 | 6 | 2（D ≤ N/2） | 2 | 小库、研究型用户、愿意手工治理 |

**不提供「完全关闭治理」开关**（见 §7 Q5）。

### 4.7 质量度量指标（验收基线）

> **前提**：P0-0 必须先跑一次基线统计，否则所有"下降/提升"都是空谈。
>
> **基线已测（2026-08-30，生产 D1 全库快照）**：N=299 书签、D=223 标签、A=366 分配。
> 复测命令：`node scripts/tag-quality-baseline.mjs`（需 `CLOUDFLARE_API_TOKEN`）。
> 注意：下表"现状"是**全库存量快照**（历史所有整理/手工标签的累积结果），不是单次整理
> 的产出；治理上线后，单次整理的指标由 `quality` 对象实时上报（P1-7），两者口径不同，
> 对比时以"新整理批次 vs 本基线"为准。

| 指标 | 定义 | 目标值 | 现状（2026-08-30 实测） |
|---|---|---|---|
| 不同标签总数 D | 一次整理产出的去重标签数 | ≤ D_max(N) | 全库 223（N=299 时预算 100，**超 2.2 倍**） |
| **孤立标签率** | 有效支持度=1 的标签数 / D | **≤ 5%** | **70.4%**（157/223，owner 反馈"太多"被量化证实） |
| 平均支撑度 | 标签分配总数 / D | **≥ 3**（均衡档实际 ≈7.5） | **1.64**（366/223） |
| 词表复用率 | 落在已有标签上的分配数 / 分配总数 | **≥ 70%**（冷启动词表为空时豁免） | 运行时指标，见 `quality.reuseRate`（P1-7） |
| 新标签占比 | 新标签数 / D | **≤ 30%** | 运行时指标，见 `quality.newTags`（P1-7） |
| 头部集中度 | 前 20% 标签覆盖的分配数 / 分配总数 | **≥ 60%** | **57.9%**（top-45 覆盖 212/366） |
| 0 标签书签率 | 最终无标签的书签数 / N | **≤ 1%** | **40.1%**（120/299） |
| 单标签书签率 | 最终只有 1 个标签的书签数 / N | **≤ 10%** | **9.4%**（28/299，达标） |
| 治理耗时 | `governTaxonomy` 执行耗时 | **< 200ms**（N=1000） | 已达标（单测断言，N=1000 < 200ms） |
| 确定性 | 同输入跑两次 | 结果集合**完全一致** | 已达标（单测断言） |

**基线解读**：孤立标签率 70.4% 与 0 标签书签率 40.1% 是两大病灶——前者是"碎片标签泛滥"
（治理 R2/R3 直接打击），后者是"大量书签从未被打标"（属覆盖问题，治理的兜底保证只覆盖
*参与整理*的书签，未参与整理的存量书签不在本次范围）。头部集中度 57.9% 已接近 60% 目标，
说明少数高频标签承担了主要组织作用，长尾 157 个孤立标签几乎不产生价值。

## 6. 安全边界与非目标

### 安全边界（强制）

1. **治理只改建议，不动存量**：自动治理**不得**执行 `DELETE FROM tags` / `UPDATE tags` / 自动 merge。已有标签的合并与清理，只通过 T1 已建的 TaxonomyPanel 由用户人工确认执行。
2. **治理后不得出现 0 标签书签**：任何被丢弃的分配，必须通过近义/上卷/域名兜底补回至少 1 个标签。
3. **治理必须确定性**：纯算法、无随机、无模型调用（P0/P1），同输入同输出，可回归。
4. **延迟护栏**：`governTaxonomy` 耗时 < 200ms（N=1000），不得成为新的超时源。

### 非目标（本次不做）

- ❌ 不做标签的语义向量化 / embedding 相似度（成本与复杂度过高，字符串+别名+词表层级已能覆盖 80% 场景）
- ❌ 不做多语言标签的跨语言合并（`AI` vs `人工智能` 依赖别名表，不引入翻译调用）
- ❌ 不改 `autoApplyThreshold` 的人工确认默认策略（默认 1 = 始终人工确认，治理的低风险性依赖这一点）
- ❌ 不重构 `scoreTagCandidate` 的打分模型（治理只在其**下游**加约束，不动打分权重本身）
